# Releasing MyPRs

## Cut a release

```bash
git tag v0.1.0
git push origin v0.1.0
```

The `Release` workflow builds, signs, notarizes and staples the app, packages
`MyPRs-0.1.0.dmg`, signs it for Sparkle, and publishes a GitHub Release with the
DMG and `appcast.xml`. Installed apps find updates through
`releases/latest/download/appcast.xml`.

Releases are cut from `main` only: the first step of the workflow fails unless
the tagged commit is an ancestor of `origin/main`.

The marketing version comes from the tag (without the `v`); the build number is
the workflow run number.

## Supply chain

- Every action in `.github/workflows` is pinned to a full commit SHA with the
  version in a trailing comment. To bump one, resolve the tag with
  `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` (dereference annotated tags via
  `git/tags/<sha>`), then update the SHA and comment together.
- `actions/checkout` runs with `persist-credentials: false`; the only step that
  talks to GitHub with a token is `gh release create`, which gets `GH_TOKEN` explicitly.
- CI has `permissions: contents: read`; the release workflow has `contents: write` only.
- Tools are pinned too: Sparkle's tarball is checked against `SPARKLE_SHA256` in
  `release.yml`, XcodeGen is installed by `scripts/install-xcodegen.sh` (version +
  SHA-256), and create-dmg by `scripts/install-create-dmg.sh` (pinned commit).
  When bumping Sparkle, update `SPARKLE_VERSION`, `SPARKLE_SHA256`
  (`shasum -a 256` of the official `Sparkle-<version>.tar.xz`) and the SPM version in
  `project.yml` together.
- The release job declares `environment: release`. That environment requires
  approval from the owner and only allows `v*` tags to deploy; a tag ruleset
  restricts creating `v*` tags to admins. The job does not start (and no secret
  is exposed) until the owner approves the deployment. The release secrets are
  still repository-level secrets; only the gate lives on the environment.

## Signed appcast

The app sets `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction`, so
Sparkle only accepts a feed carrying an EdDSA signature (made with the same key
as the DMG, verified against `SUPublicEDKey`) and verifies the archive signature
before extracting it. `make-appcast.sh` writes the unsigned feed, then the
workflow runs `sign_update --ed-key-file - appcast.xml`, which embeds the
signature as a trailing `sparkle-signatures` XML comment. Any later edit of
`appcast.xml` invalidates it, so re-run `sign_update` after changing the file.
Versions before this change do not require a signed feed and ignore the comment.

## DMG window

`scripts/make-dmg.sh <app> <dmg>` builds the installer with `create-dmg`: styled
background, app icon on the left, Applications link on the right. The background
is generated by `scripts/dmg/make-background.swift` (run it, then
`tiffutil -cathidpicheck background.png background@2x.png -out background.tiff`
inside `scripts/dmg`) and the outputs are committed. `create-dmg` positions icons
through Finder, so it needs a GUI session (GitHub macOS runners have one).

## Secrets

Add these under GitHub repo Settings > Secrets and variables > Actions.

| Secret | What it is |
|---|---|
| `DEVELOPER_ID_CERT_P12_BASE64` | Developer ID Application certificate with private key, as base64 |
| `DEVELOPER_ID_CERT_PASSWORD` | Password chosen when exporting the .p12 |
| `APP_STORE_CONNECT_KEY_ID` | Key ID of the App Store Connect API key |
| `APP_STORE_CONNECT_ISSUER_ID` | Issuer ID shown on the API keys page |
| `APP_STORE_CONNECT_KEY_P8_BASE64` | The downloaded `AuthKey_XXXX.p8`, as base64 |
| `SPARKLE_PRIVATE_KEY` | Sparkle EdDSA private key |

### Developer ID certificate

1. In Xcode > Settings > Accounts > Manage Certificates, create a
   "Developer ID Application" certificate (or create it at developer.apple.com).
2. Open Keychain Access > My Certificates, right-click the certificate (expand it
   to be sure the private key is included) > Export, format `.p12`, set a password.
3. `base64 -i DeveloperID.p12 | pbcopy` and paste as `DEVELOPER_ID_CERT_P12_BASE64`.

### App Store Connect API key (notarization)

1. appstoreconnect.apple.com > Users and Access > Integrations > App Store Connect API.
2. Generate a key with the Developer role. Note the Key ID and the Issuer ID.
3. Download `AuthKey_XXXX.p8` (only possible once).
4. `base64 -i AuthKey_XXXX.p8 | pbcopy` and paste as `APP_STORE_CONNECT_KEY_P8_BASE64`.

### Sparkle keys

Download the Sparkle release tarball matching `SPARKLE_VERSION` in the workflow
and run (keep the SPM version in `project.yml` on the same release):

```bash
./bin/generate_keys            # stores the private key in your login keychain, prints the public key
./bin/generate_keys -x sparkle_private_key   # exports the private key to a file
```

- Put the printed public key in `project.yml` as `SUPublicEDKey` (already done for the
  current key pair; only needed again if the keys are rotated).
- Put the contents of `sparkle_private_key` in `SPARKLE_PRIVATE_KEY`, then delete the file.

## Signing notes

- The release build uses manual signing with the Developer ID certificate and no
  provisioning profile. The only entitlement needing a team-prefixed identifier is
  the App Group (`688YYDN5Z4.com.zaintech.myprs`), which macOS accepts without a
  profile for Developer ID apps. If `xcodebuild archive` or export complains about
  a missing profile, create a Developer ID provisioning profile for the app and
  the widget in the developer portal and install it in the workflow.
- Sparkle's nested helpers are re-signed by Xcode during export.

## Widget still shows the previous version after an update

First check the app and embedded widget versions in their Info.plist files.
If both are current but chronod reports `Bundle version did not match`, an old
widget extension process may have survived the update. Compare its start time
with the installation time before changing any caches.

Quit only the stale `MyPRsWidget` process, re-register `/Applications/MyPRs.app`
with LaunchServices (`lsregister -f`), then restart `chronod`. This preserves
widget placement and configuration. Confirm `Reload success` for the affected
widget in chronod logs. Do not clear the entire WidgetKit database or restart
the app for this condition.
